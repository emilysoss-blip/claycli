## 10-account test

Run as the guide prescribes: one row first (`csv run --limit 1`), then rows 2-10 from a new
file, because `--limit` has no offset. Results are in `../data/cli_test10_results.csv`.

| Tier | Accounts |
|---|---|
| Tier 1 (100) | UnitedHealth Group, HCA Healthcare, CommonSpirit Health, Marsh, GE Vernova, Honeywell Technologies, State Farm |
| Tier 2 (75) | Lockton (412 open jobs), Johns Hopkins (238). Both are below the 500-job calibration bar |
| Review (80 / 100 possible) | Kaiser Permanente: no HR tech returned for kp.org; the Claygent found no stated evidence, so HCM stays unknown |

- **10 of 10 runs completed** with 0 failed steps.
- **52 credits:** 5 per account (4 action + 1 data), plus 2 for the one Claygent call.
- **The Claygent ran once in 10.** The gate routed only the account whose HCM was unknown
  and could still change the tier.
- **Identity:** the 5 LinkedIn-pinned rows (HCA, Johns Hopkins, CommonSpirit, Kaiser, Marsh)
  all enriched as the intended parent. CommonSpirit came back at 48,637 employees; its domain
  never returns the parent at all.

### What the test surfaced

1. **The HR-tech filter is fuzzy, so the rule has to be exact.** PredictLeads'
   `technologyNameFilter` matched "Talend", "C", "DCatalog" and "Teleopti" alongside the real
   systems, and returned "Workday Financial Management" and "Workday Prism Analytics". Those
   are Workday products but not evidence of Workday HCM. The tiering node now matches exact
   product names per item (`HCM_ALIASES` in `build/node_code.py`). No tier changed on these
   10, because every Tier 1/2 account also had a genuine HCM or ATS.
2. **Marsh shows -57% headcount over 3 months. That is the rename, not a layoff.** Employees
   moved from the closed Marsh McLennan page to the Marsh page. A News or headcount-reduction
   trigger would misfire here, which is the guide's warning about treating reductions as
   signals without review.
3. **Johns Hopkins enriched as Johns Hopkins Medicine only** (39,514 employees, 238 jobs).
   The University is a separate employer with its own CHRO. The full run should take
   `divisions.csv` rows, not parent rows, for multi-entity accounts.
4. **Open-job counts come from `identifiers_only` mode** (up to 500 postings per call), so
   "500+" is the ceiling of what one call can see. UnitedHealth Group returned 543, so the
   cap is soft; treat the number as a floor.

## Signal: blocked on population

The "new talent leader" signal (`NewHire`) needs a watched population. `clay signals create
--help` confirms the shape the corrections file describes, `{"entityType":"ACCOUNT",
"segmentIds":[...]}` at the top level. The population is the problem:

- **Audience segment by LinkedIn URL over-matches.** `Equal` on a URL field behaves as a
  prefix match: `linkedin.com/company/chase` also matched Chase Interaction and ChaseLabs,
  and `mercer` matched Mercer Advisors. The 51-URL filter matched 867 records, and only 43
  of a 100-record sample were cohort entities.
- **URL plus domain is tighter, but still not exact.** 137 records, 122 exact, 15 strays
  (domain `Contain` is also a substring: "chase.com" catches catiechase.com). 14 cohort
  entities have no audience record at all, including CommonSpirit Health, Johns Hopkins
  Medicine, the University and the Marsh parent.
- **A table-watched signal would be exact, but the CLI cannot create tables.** It can only
  read them.

`clay signals list` also fails in this workspace with `contract_mismatch` at
`triggerDefinitions.939.signal.settings`, so the duplicate check has to be done in the app.
